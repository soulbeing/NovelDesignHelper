# 小说项目存储、兼容性与 GitHub 版本历史实施计划

更新日期：2026-10-12

状态：用户已要求实施，第一版核心功能已实现。本文件用于跨会话接续工作；实际范围与验证证据见第 12 节。

## 1. 用户目标与已确定要求

用户准备开始真实写作，并在使用中持续改进软件。因此软件版本递进时，已有作品必须仍能读取、编辑和保存，不能因模型变化丢失内容。

用户最初提出“另存为”，实际目的为版本追溯；随后明确改用用户指定的 GitHub 小说仓库保存版本，不再需要以另存为承担这项功能。

确定的要求：

- 软件源码仓库是 public；小说数据进入用户指定的 GitHub 仓库，与源码仓库分开。
- 创建小说项目时提供小说仓库信息与 GitHub Key/Token。
- 推荐 private 小说仓库，但是否 private 由用户决定，软件不擅自更改可见性。
- 内置保存功能：本地持久化，并上传至指定小说仓库，以实现版本追溯。
- 在软件持续演进过程中保证历史数据兼容。
- 提供几个 starting templates，便于新建作品。
- 将兼容与存储约束写入 agent 文件：已写入项目根目录 `AGENTS.md`。
- 初始任务仅整理计划；随后用户明确要求 implement，已授权本地实现与验证。真实仓库和 Token 由用户在软件中配置，本轮未上传真实小说。

## 2. 已检查的项目现状

| 位置 | 当前职责与限制 |
| --- | --- |
| `shared/board.ts` | Zod 定义 Board；`version` 只接受 1；包含标题、故事核心、节点、位置、节点内容和关系；没有版本迁移 |
| `src/useBoard.ts` | 读取服务器故事板、本机备份、700 ms 延迟自动保存、串行请求、撤销重做；仅支持单故事板 |
| `server/app.ts` | GET/PUT `/api/board`；写入 `data/board.json`；临时文件加 rename 原子替换；没有多项目、版本列表或 GitHub 同步 |
| `src/App.tsx` | JSON 导入替换当前故事板，JSON/Markdown 导出；没有项目创建或版本历史 UI |
| `shared/templates.ts`、`shared/chapterTemplates.ts`、`src/TemplateLibrary.tsx` | 剧情插入模板；与新建作品的起始模板用途不同 |
| `tests/board.test.ts`、`tests/server.test.ts`、`tests/templates.test.ts` | 已有 Node test/tsx 测试基础，无须另引入大型回归测试框架 |

现有读取失败不会主动替换损坏的服务器文件；改造时保留这项性质。当前 schema 对未知字段的处理必须审查，不能把“解析成功”误认为“所有数据都保留”。

限制：保存/导入请求目前 2 MB，最多 1500 个节点、5000 条关系；第一阶段不自动扩大这些限制。

工作区存在用户此前的未提交修改，涉及 README、App、样式与剧情模板文件。实施前再次检查 `git status` 和适用的 `AGENTS.md`，保留这些修改，不能重置或覆盖。

## 3. 推荐总体方案（与已确定要求区分）

采用“版本化 JSON 项目文件 + 本地自动保存 + GitHub 提交历史 + app 内预览/恢复”。

- 自有 JSON 是完整、可往返的作品格式。未来需要互通时另做 JSON Canvas 导入导出，不在首阶段强制改成 `.canvas`。
- 作品格式版本独立于软件发行版本；界面和业务代码变化不必升级格式。
- 每个项目有稳定 ID，改名不会改变其本地或远端路径。
- 一个小说仓库可容纳多个项目，建议远端路径为 `projects/<projectId>/story.json`。
- JSON 导出仍保留，用于独立备份与迁移，不切换当前项目。
- Node 服务负责远端 API 调用和写入协调；前端负责创作与状态展示。
- 第一版建议通过 GitHub REST API 创建提交，不要求安装 Git，也不声称本地目录已有 Git 历史。
- 远端历史是 GitHub commits；本地文件是当前工作副本。离线命名版本需额外保存本地检查点，避免多次离线“保存版本”被压缩成最后一份草稿。

GitHub 历史保留文件并不能代替文件格式迁移；打开旧提交也必须走兼容读取流程。

## 4. 第一部分：数据兼容性与本地存储

这一部分先完成并验证，再接 GitHub，避免把本地数据问题与远端同步问题混在一起。

### 4.1 固化 v1 兼容基线

- 将当前 v1 文件格式制作成固定的、合成故事测试样本，提交到专用 fixtures 目录。
- 样本覆盖中文、多行内容、空字段、不同卡片类型、负坐标、分支/循环关系和可选关系标签。
- 历史 fixture 不从当前 `createExample()` 动态生成；后续不能为了让测试通过而更新旧样本。
- 不将真实小说或 Token 放入源码仓库或测试样本。

### 4.2 定义最小持久化合同

基于现有 Board 建模，避免预先定义章节系统、附件系统或协作模型。

区分三类数据：

1. 作品内容与布局：标题、故事核心、卡片 ID/类型/文本、位置、关系；可包含当前需要的视图位置与缩放。
2. 项目标识与格式：稳定项目 ID、格式标识/版本；具体字段名实施时统一。
3. 本机连接与同步配置：仓库、分支、远端路径、同步基线、待上传队列；保存在本机，不混入作品正文。

Token 独立于上述作品文件，不写入导出、备份、GitHub commit 或日志。组件状态、选中卡片、临时错误、API Key 不进入作品格式。

迁移旧 v1 单故事板为新项目时，只分配一次项目 ID 并持久化；重复打开不能生成另一个项目。历史文件缺少新字段时使用明确的迁移规则，不能凭标题猜测项目身份。

### 4.3 统一兼容读取与序列化

建议设立共享的解析入口，具体名称不强制：

```text
原始数据 → 判断格式与版本 → 校验对应历史格式
         → 顺序迁移 → 校验当前格式 → 可编辑作品
```

适用入口包括服务器磁盘读取、JSON 导入、本机恢复、GitHub 当前文件、历史版本和检查点恢复。

- 新版持续支持旧版；迁移链按 v1 → v2 → 后续版本组织。
- 不认识的未来版本明确拒绝；不自动降级或删字段。
- 未知字段制定显式规则：在受控扩展字段中无损保留，或拒绝具有未知数据的输入并保留原件；不得静默剥离。
- 导入/迁移先在内存中完成校验，失败不能改变当前作品。
- 读取迁移不立即覆盖原文件；首次落盘升级前先保存可恢复的原始副本。
- 用稳定的 JSON 序列化顺序和缩进，减少 GitHub 无意义差异；仅查看文件不能刷新时间字段并制造提交。

### 4.4 多项目本地保存与恢复

- 从 `data/board.json` 迁移为按项目 ID 存储，具体目录结构以最小实现为准。
- 初次升级发现旧文件时先备份、迁移、验证，保留旧文件；重复启动不得重复导入或覆盖新项目。
- 新增项目列表、创建、打开与切换；新项目使用用户选择的起始模板。
- 保存维持串行协调、临时文件加原子替换，并保留可恢复上一份副本。
- 自动保存、本机备份、恢复草稿、撤销历史均按项目隔离。
- 请求在发起时捕获项目 ID 和内容版本；切换项目后，旧回调不能改变新项目的状态或写入目标。
- 本地保存失败要明确显示；不能提前标记已保存或已同步。
- 磁盘损坏或格式不支持时保留原件，进入可恢复错误状态；不得以示例或空白作品替代后自动覆盖。

### 4.5 第一部分验收标准

- [x] 原有 v1 JSON 导出及旧 `data/board.json` 均可打开，内容、ID、关系、坐标保留。
- [x] 升级和再次启动不会重复创建项目，迁移原件可恢复。
- [x] 保存后重新打开、导出后重新导入，数据语义一致。
- [x] 损坏文件、未知字段策略和未来版本都有可验证的行为，拒绝时不覆盖。
- [x] 切换项目期间延迟保存与恢复不会串写；撤销不会带入另一项目。
- [x] 保存失败不宣称成功，原子替换及备份行为经测试验证。
- [x] 相关测试、完整 `npm test` 与 `npm run build` 通过。

## 5. 第二部分：用户指定的 GitHub 小说仓库

### 5.1 配置与权限验证

- 新建项目流程包含仓库地址、分支、Token 与模板；与本地创建流程整合。
- 支持选择已有仓库；首版不默认代建仓库或修改可见性。
- 验证仓库存在、可见性、目标分支、文件路径与凭据权限。优先采用限定目标仓库的 fine-grained PAT，Contents 读写权限。
- 默认分支取仓库信息，不硬编码 `main`；空仓库的初始化行为必须明确实现和测试。
- public 仓库显示小说会公开的事实，让用户自行决定；不静默改为 private。
- 新建远端路径已存在时，提供打开已有项目或换用独立路径；不覆盖已有小说。
- 自定义分支/路径与本机目录都要校验，避免任意路径写入。
- 不把应用源码仓库预填为小说上传目标。

### 5.2 保存、提交与失败状态

推荐将频繁本地保存与远端提交分开：

- 本地修改及时自动保存。
- “保存版本”：立即创建命名检查点并提交，用户可填写版本说明。
- “自动同步”：有内容变化时按间隔提交，建议五分钟；未变更则跳过。
- 离线时仍可编辑；本地保留最新草稿及显式命名检查点，恢复连接后按顺序处理。
- 队列与检查点持久化，重启不能忘记尚未上传的版本；自动保存可合并，命名版本不能丢。
- UI 分别显示本地保存状态、远端同步状态、上次成功时间和待上传数量。
- 每次提交绑定确切快照；成功响应不能把响应期间产生的新修改标为已同步。
- API 超时后可能已经提交：重试前检查远端状态，识别已完成操作，避免重复版本或误报冲突。

### 5.3 并发与冲突

- 记录最后读取/同步的远端文件 SHA 与历史提交标识；区分文件 blob SHA 与 commit SHA。
- 基于期望远端版本提交；不能先取最新 SHA 再无条件覆盖远端内容。
- 远端文件变化时停止该项目上传，保留本地内容和远端副本，让用户决定后续处理。
- 第一版不做任意 JSON 自动合并，不 reset、不 force-push、不重写历史。
- 使用 Contents API 时，文件 SHA 可检测该文件变化；若要求整个分支 HEAD 不变，需选择支持对应引用并发检查的方案，不能声称文件 SHA 已覆盖全部分支并发情况。
- 验证 Token 过期、无权限、受保护分支、网络错误与限流；这些情况不影响本地写作。

## 6. 第三部分：历史列表、预览与恢复

- 按项目远端路径读取历史，支持分页；显示提交时间、说明和版本标识。
- 使用明确的 commit SHA 读取历史文件，不用当前分支内容冒充历史版本。
- 预览只读，不触发本地自动保存、迁移落盘或远端提交。
- “恢复此版本”先保留当前草稿，再经兼容迁移与校验，将历史内容安装为当前项目的新版本。
- 恢复沿用当前项目 ID 与仓库绑定，不能用旧文件修改本机配置或凭据。
- 提交说明标明恢复源；断网时先保存本地恢复版本，之后正常上传。
- 恢复失败或历史格式不支持时，当前作品与历史原件均保留。
- 恢复后可以再次恢复恢复前的内容，历史保持完整。

首版不承诺逐字段可视化 diff、分支管理、多人实时协作或离线完整 Git 镜像。

## 8. 自动回归测试与验证方法

沿用现有 test/tsx 框架。外部行为使用模拟 GitHub 响应，不在常规测试中写入真实仓库。

必测范围：

- 历史 fixture 加载与迁移；文本、关系、ID、布局语义保持。
- 当前格式保存/加载、导出/导入往返；迁移幂等性和失败不覆盖。
- 旧本地存储升级、多项目写入隔离、损坏文件和中断写入处理。
- 本地成功/远端失败、Token 无效、限流、过期 SHA、受保护分支。
- 请求途中继续编辑、切换项目、重启恢复队列、超时后重试去重。
- 历史分页、按提交读取、只读预览、恢复形成新提交。
- Token 不进入作品、导出、日志、恢复草稿或提交请求的文件内容。
- 起始模板结构有效、重复创建身份独立。

为异步前端行为选择最小必要的测试工具；仅在现有框架无法验证关键竞态时增加依赖，不先引入整套复杂基础设施。

每阶段完成运行相关测试，阶段交付运行 `npm test` 与 `npm run build`。最后按用户路径人工验证：创建 → 编辑 → 本地保存 → 提交 → 继续修改 → 查看旧版本 → 恢复 → 重启打开。

真实 GitHub 验证使用用户指定的测试目标与已授权操作；不向未知或源码仓库发布数据。不能把模拟测试通过写成真实 GitHub 联调成功。

### 第一版明确范围与限制

- 支持 github.com 已初始化仓库和已存在分支。空仓库需先在 GitHub 添加 README；首版不自动初始化空仓库、不代建仓库、不管理分支。
- 自动同步由当前项目页面每五分钟触发，页面关闭或项目切换后其他项目队列仍落盘，重新打开可继续上传。
- Token 只在当前 Node 进程会话保留。元信息可验证仓库访问，最终 Contents 写入权限与分支保护在首次提交时确认。
- 远端 SHA 冲突时保留双方内容，支持查看/下载远端副本；尚无交互合并工具或自动合并。可导出双方、人工整理并以新项目/新路径发布，原历史保留。
- 备份 `.bak` 的损坏恢复暂由用户停服后手动复制，未增加单独自动修复界面。
- 尚未进行用户真实 private 仓库联调，也未进行 iOS 真机测试。以上模拟与页面验证不能替代这两项。
